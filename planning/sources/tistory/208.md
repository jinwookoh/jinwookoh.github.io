# 옵저버 패턴 vs Pub/Sub 패턴

원문: https://jinwookoh.tistory.com/208

"상태가 변할 때마다, 관련된 다른 객체들에게 알려줘야 한다."

이 요구사항을 해결하기 위해 우리는 **옵저버 패턴(Observer Pattern)**을 사용합니다. 유튜브의 '구독 알림'이나 엑셀의 '수식 자동 계산'이 대표적입니다.

하지만 면접이나 실무 아키텍처 회의에서 "옵저버 패턴과 Pub/Sub 패턴의 차이가 뭔가요?"라는 질문을 받으면 말문이 막히는 경우가 많습니다. 오늘은 이 두 가지 방식의 결정적인 차이와, 실무(Spring)에서의 적용법을 정리해 봅니다.

## 1. 고전적 옵저버 패턴 (Classic Observer) - "직거래"

GoF 디자인 패턴에서 정의하는 원형입니다. 주체(Subject)와 관찰자(Observer)가 **서로를 인지하고 직접 소통**합니다.

### 구조

- Subject (주체): 이벤트를 발생시키는 객체. List<Observer>를 들고 있습니다.

- Observer (관찰자): 알림을 받는 객체.

### 코드 예시 (Java)

Java

```
// 1. 관찰자 인터페이스
interface Observer {
    void update(String msg);
}

// 2. 주체 (유튜버)
class Youtuber {
    private List subscribers = new ArrayList<>();

    public void subscribe(Observer o) { subscribers.add(o); }

    public void uploadVideo(String title) {
        // 주체가 구독자들의 메서드를 직접 호출 (동기 방식)
        for (Observer s : subscribers) {
            s.update(title + " 영상이 업로드 되었습니다.");
        }
    }
}

// 3. 사용
Youtuber me = new Youtuber();
me.subscribe(msg -> System.out.println("구독자1 알림: " + msg));
me.uploadVideo("디자인패턴 강의");

```

### 장단점

- 장점: 구조가 간단하고 직관적입니다.

- 단점: 강한 결합(Tight Coupling): Subject가 Observer의 존재를 알고 있어야 합니다.

- 동기적 실행: Observer가 100만 명이면, 알림을 다 돌릴 때까지 uploadVideo() 메서드는 끝나지 않습니다.

## 2. 발행-구독 패턴 (Pub/Sub Pattern) - "중개거래"

옵저버 패턴의 확장판이자 현대적인 아키텍처입니다. 둘 사이에 **중개자(Broker / Event Bus)**를 두어 서로를 전혀 모르게 만듭니다.

### 차이점

- 옵저버 패턴: Subject -> Observer (직접 호출)

- Pub/Sub 패턴: Publisher -> [Event Channel] -> Subscriber (채널을 통해 전달)

### 코드 예시 (가상의 EventBus 활용)

Java

```
// 1. 발행자 (Publisher)
class Publisher {
    public void publish(String topic, String msg) {
        // 누가 듣고 있는지 모름. 그냥 채널(Broker)에 던짐.
        EventBus.send(topic, msg);
    }
}

// 2. 구독자 (Subscriber)
class Subscriber {
    public Subscriber() {
        // 채널에 귀를 기울임
        EventBus.subscribe("VIDEO_UPLOAD", this::onMessage);
    }

    public void onMessage(String msg) {
        System.out.println("메시지 수신: " + msg);
    }
}

```

### 장단점

- 장점: 느슨한 결합(Loose Coupling): 발행자와 구독자는 서로 존재조차 모릅니다.

- 비동기 처리 용이: 메시지 큐(Kafka, RabbitMQ) 등을 중개자로 쓰면 대용량 처리가 가능합니다.

- 단점: 시스템 복잡도가 올라가고, 메시지가 제대로 도착했는지 보장하기 위한 추가 로직이 필요할 수 있습니다.

## 3. 실무에서의 적용 (Spring Framework)

스프링 개발자라면 직접 List를 만들어 옵저버 패턴을 구현하기보다, 스프링이 제공하는 **ApplicationEvent** 기능을 쓰는 것이 표준입니다. (내부적으로 Pub/Sub 모델과 유사하게 동작합니다.)

### Spring Event 방식 (@EventListener)

Java

```java
// 1. 이벤트 객체 정의
public class VideoUploadEvent {
    private String title;
    // 생성자, getter ...
}

// 2. 발행자 (Publisher)
@Service
@RequiredArgsConstructor
public class VideoService {
    private final ApplicationEventPublisher eventPublisher;

    public void upload(String title) {
        // 로직 수행 후 이벤트 발행
        eventPublisher.publishEvent(new VideoUploadEvent(title));
    }
}

// 3. 구독자 (Listener)
@Component
public class NotificationService {
    @EventListener
    @Async // 비동기로 처리하고 싶다면 추가
    public void handleVideoUpload(VideoUploadEvent event) {
        System.out.println("알림 발송: " + event.getTitle());
    }
}

```

이 방식을 쓰면 VideoService는 NotificationService를 전혀 의존하지 않게 되어(import조차 안 함), 완벽한 **OCP(개방-폐쇄 원칙)** 를 지킬 수 있습니다.

## 요약: 무엇을 언제 써야 할까?

| 구분 | Observer Pattern (Classic) | Pub/Sub Pattern (Modern) |
|---|---|---|
| 통신 방식 | 직접 통신 (Synchronous) | 중개자 통신 (Asynchronous) |
| 결합도 | 주체가 관찰자를 알고 있음 (Coupled) | 서로 모름 (Decoupled) |
| 구현 난이도 | 쉬움 (메모리 내 처리) | 어려움 (메시지 브로커 필요 가능성) |
| 추천 상황 | UI 이벤트 처리, 단일 애플리케이션 내부 로직 | 마이크로서비스 간 통신, 대규모 알림 시스템 |

### 결론

"객체 간의 결합도를 낮추고 싶다"면 옵저버 패턴을 떠올리세요.

하지만 단순히 객체 간 통신이라면 Classic Observer를, 시스템 모듈 간의 디커플링과 비동기 처리가 필요하다면 Pub/Sub(Spring Event) 방식을 선택하는 것이 정답입니다.

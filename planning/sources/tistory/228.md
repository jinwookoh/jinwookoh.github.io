# 의존성 주입(DI) 패턴 완벽 정리

원문: https://jinwookoh.tistory.com/228

"객체 A가 객체 B를 사용하려면, A가 B를 new로 생성해야 합니다."

하지만 이렇게 하면 A와 B가 강하게 결합되어 테스트나 확장이 어려워집니다.

이를 해결하기 위해 **"외부에서 B를 만들어서 A에게 넣어주는(Inject)"** 것이 **의존성 주입(DI)**입니다. 스프링에서는 @Autowired 어노테이션이 이 역할을 하는데, 이걸 **어디에 붙이느냐**에 따라 코드의 품질이 결정됩니다.

## 1. 방식 1: 필드 주입 (Field Injection) - "달콤한 독사과"

코드가 가장 짧고 간결해서, 예제 코드나 초보 개발자들이 가장 많이 사용하는 방식입니다. 멤버 변수(필드) 위에 바로 @Autowired를 붙입니다.

### 코드 예시

Java

```java
@Service
public class OrderService {
    // 필드에 바로 주입 (매우 간편함)
    @Autowired
    private MemberRepository memberRepository;

    public void createOrder() {
        memberRepository.save(...);
    }
}

```

### 치명적 단점 (Anti-Pattern)

- 테스트 불가능: 스프링 컨테이너 없이 순수 자바 코드로 단위 테스트를 하려면, memberRepository에 가짜 객체(Mock)를 넣어줄 방법이 없습니다. (private이라 접근 불가, Setter도 없음)

- NPE 위험: 의존성이 주입되지 않아도 객체 생성이 되어버립니다. 나중에 메서드를 호출할 때 NullPointerException이 터집니다.

- 순환 참조 감지 어려움: A가 B를, B가 A를 참조하는 경우, 애플리케이션이 구동되다가 스택 오버플로우로 죽을 때까지 모를 수 있습니다.

## 2. 방식 2: 수정자 주입 (Setter Injection) - "선택적 의존성"

필드 대신 setXXX 메서드에 @Autowired를 붙이는 방식입니다. 과거 스프링 문서에서 자주 보이던 방식입니다.

### 코드 예시

Java

```java
@Service
public class OrderService {
    private MemberRepository memberRepository;

    // Setter 메서드를 통해 주입
    @Autowired
    public void setMemberRepository(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}

```

### 장단점

- 장점: 의존성이 **선택적(Optional)**이거나, 실행 중에 의존성을 변경해야 할 때 유용합니다.

- 단점: public 메서드이므로, 누군가 실행 중에 실수로 setMemberRepository(null)을 호출하여 멀쩡한 객체를 고장 낼 위험이 있습니다.

## 3. 방식 3: 생성자 주입 (Constructor Injection) - "스프링의 표준"

Spring 4.3부터 권장되는 **가장 완벽한 방식**입니다. 생성자를 통해 의존성을 주입받습니다.

### 특징

- 불변성(Immutability): 필드를 final로 선언할 수 있습니다. 한 번 주입되면 평생 변하지 않습니다.

- Lombok 결합: @RequiredArgsConstructor와 함께 쓰면 코드가 매우 깔끔해집니다.

### 코드 예시

Java

```java
@Service
public class OrderService {
    // final 키워드 사용 가능! (불변성 보장)
    private final MemberRepository memberRepository;

    // 생성자가 하나면 @Autowired 생략 가능 (Spring 4.3+)
    public OrderService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}

// Lombok 사용 시 (실무 스타일)
@Service
@RequiredArgsConstructor
public class OrderService {
    private final MemberRepository memberRepository;
}

```

### 왜 이것이 정답인가?

- 컴파일 타임 안전성: new OrderService()를 호출할 때 인자를 안 넣으면 컴파일 에러가 납니다. 즉, 의존성 누락을 원천 봉쇄합니다.

- 테스트 용이: 단위 테스트 시 new OrderService(new MockRepository()) 처럼 생성자로 가짜 객체를 쉽게 주입할 수 있습니다.

- 순환 참조 방지: A와 B가 서로를 생성자에서 참조하면, 스프링이 앱 구동 시점에 "BeanCurrentlyInCreationException"을 띄워주며 바로 잡아냅니다.

## 요약: 어디에 @Autowired를 붙일까?

| 구분 | Field Injection (필드) | Setter Injection (수정자) | Constructor Injection (생성자) |
|---|---|---|---|
| 코드 간결성 | 최상 (어노테이션 하나) | 중간 (메서드 필요) | 상 (Lombok 사용 시) |
| 의존성 변경 | 불가능 | 가능 (Runtime) | 불가능 (Immutable) |
| 테스트 용이성 | 최악 (DI 프레임워크 필수) | 좋음 | 최상 (순수 자바 가능) |
| Null 안전성 | 낮음 (NPE 위험) | 낮음 | 완벽 (컴파일 에러) |
| 권장 여부 | 비추천 (안티 패턴) | 선택적 사용 | 강력 추천 (표준) |

### 결론

"필드 주입(@Autowired private)"은 데모용 코드나 테스트 코드(@SpringBootTest)에서만 사용하세요.

실무 애플리케이션 코드를 짤 때는 무조건 **생성자 주입(final + @RequiredArgsConstructor)**을 사용하는 것이 버그를 줄이고 테스트하기 좋은 코드를 만드는 비결입니다.

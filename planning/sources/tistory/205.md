# [디자인패턴] 전략 패턴(Strategy Pattern) 완벽 정리: if-else 지옥에서 탈출하는 4가지 방법

개발을 하다 보면 비즈니스 로직이 복잡해질수록 if-else나 switch 문이 끝도 없이 길어지는 경험을 하게 됩니다.

Java

```
// 이런 코드가 보인다면 리팩토링이 필요합니다.
if (type.equals("KAKAO")) {
    // 카카오 결제 로직...
} else if (type.equals("NAVER")) {
    // 네이버 결제 로직...
} else if (type.equals("TOSS")) {
    // 토스 결제 로직...
}

```

이런 코드는 새로운 결제 수단이 추가될 때마다 기존 코드를 수정해야 하므로 **OCP(개방-폐쇄 원칙)**를 위반하게 됩니다. 오늘은 이 문제를 해결하는 **전략 패턴(Strategy Pattern)**의 정석적인 방법부터, 실무(Spring Boot)에서 자주 사용하는 최적화 패턴까지 단계별로 정리해 봅니다.

## 1. 전략 패턴의 정석 (Basic Strategy)

가장 기본적인 전략 패턴은 **"런타임(실행 중)에 알고리즘을 선택하여 주입"**하는 방식입니다.

### 핵심 구조

- Strategy Interface: 모든 전략이 구현해야 할 공통 인터페이스

- Concrete Strategy: 실제 로직을 담은 구현체들

- Context: 전략을 사용하는 주체 (로봇, 게임 캐릭터 등)

- Client: 상황에 맞는 전략을 직접 골라 Context에 주입해주는 사용자

### 코드 예시 (Java)

Java

```
// 1. 전략 인터페이스
public interface MoveStrategy {
    void move();
}

// 2. 전략 구현체들
public class WalkStrategy implements MoveStrategy {
    public void move() { System.out.println("뚜벅뚜벅 걷습니다."); }
}

public class FlyStrategy implements MoveStrategy {
    public void move() { System.out.println("슈웅 날아갑니다."); }
}

// 3. 컨텍스트 (로봇)
public class Robot {
    private MoveStrategy moveStrategy;

    // 외부에서 전략을 주입받음 (Setter Injection)
    public void setMoveStrategy(MoveStrategy moveStrategy) {
        this.moveStrategy = moveStrategy;
    }

    public void move() {
        moveStrategy.move(); // 위임(Delegate)
    }
}

// 4. 사용 (Client)
public static void main(String[] args) {
    Robot robot = new Robot();

    robot.setMoveStrategy(new WalkStrategy());
    robot.move(); // "뚜벅뚜벅 걷습니다."

    // 실행 중에 전략 교체 가능
    robot.setMoveStrategy(new FlyStrategy());
    robot.move(); // "슈웅 날아갑니다."
}

```

**한계점:** 이 방식은 클라이언트가 "어떤 전략을 쓸지" 직접 알고 주입해줘야 합니다. 하지만 웹 개발에서는 클라이언트가 단순히 데이터(예: paymentType="KAKAO")만 보내고, **서버가 알아서 전략을 찾아야** 하는 경우가 더 많습니다.

## 2. 실무형 전략 패턴 A: Smart Strategy (supports 메서드)

스프링 프레임워크 내부(Spring Security 등)에서 가장 많이 사용하는 방식입니다. 전략 객체가 **"내가 이 요청을 처리할 수 있는지"** 스스로 판단하게 만듭니다.

### 특징

- supports(Condition) 메서드를 통해 전략 선택 로직을 각 구현체에 위임합니다.

- 조건이 단순 Key 매칭이 아니라 **복잡한 로직(가격 범위, 시간대 등)**일 때 강력합니다.

### 코드 예시

Java

```java
public interface PaymentStrategy {
    // 이 전략이 처리 가능한지 확인 (핵심)
    boolean supports(PaymentType type);
    // 실제 로직
    void pay(long amount);
}

@Component
public class KakaoPayStrategy implements PaymentStrategy {
    @Override
    public boolean supports(PaymentType type) {
        return type == PaymentType.KAKAO;
    }
    @Override
    public void pay(long amount) { /* 카카오 결제 로직 */ }
}

```

### 사용하는 곳 (Context)

Java

```java
@Service
@RequiredArgsConstructor
public class PaymentService {
    // 스프링이 모든 구현체를 List에 담아 주입해줍니다.
    private final List strategies;

    public void process(PaymentType type, long amount) {
        PaymentStrategy strategy = strategies.stream()
            .filter(s -> s.supports(type)) // 스스로 처리가능하다고 한 전략을 찾음
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException("지원하지 않는 결제 수단"));

        strategy.pay(amount);
    }
}

```

## 3. 실무형 전략 패턴 B: Map Registry (성능 최적화)

supports() 방식은 리스트를 순회해야 하므로 전략이 많아지면 성능 이슈가 있을 수 있습니다. 구분 기준이 명확한 문자열(Key)이라면 Map을 사용하는 것이 가장 빠르고 깔끔합니다.

### 특징

- if문도 없고, loop도 없습니다.

- $O(1)$의 속도로 즉시 전략을 찾습니다.

### 코드 예시

Java

```
@Service
public class PaymentService {
    private final Map strategyMap = new HashMap<>();

    // 생성자에서 Map 초기화
    public PaymentService(List strategies) {
        // 각 전략 클래스에 getStrategyName() 같은 메서드가 있다고 가정
        strategies.forEach(s -> strategyMap.put(s.getStrategyName(), s));
    }

    public void process(String payMethod, long amount) {
        // Key로 즉시 조회
        PaymentStrategy strategy = strategyMap.get(payMethod);
        strategy.pay(amount);
    }
}

```

## 4. 실무형 전략 패턴 C: Enum Strategy

로직이 아주 간단하고, 클래스 파일이 늘어나는 게 싫을 때 유용합니다.

### 코드 예시

Java

```
public enum Calculator {
    PLUS {
        int calculate(int a, int b) { return a + b; }
    },
    MINUS {
        int calculate(int a, int b) { return a - b; }
    };

    // 추상 메서드 정의
    abstract int calculate(int a, int b);
}

```

사용할 때는 Calculator.PLUS.calculate(10, 20) 처럼 바로 호출합니다.

## 요약: 어떤 방식을 선택해야 할까?

상황에 맞춰 가장 적절한 방식을 선택하는 가이드입니다.

| 패턴 방식 | 추천 상황 | 장점 |
|---|---|---|
| Basic (Setter) | 상태에 따라 행동을 동적으로 바꿔야 하는 객체 (게임 캐릭터 등) | 가장 정석적이며 이해하기 쉬움 |
| Smart (Supports) | 전략 선택 조건이 복잡할 때 (예: 금액 > 10000 & VIP 등) | OCP를 가장 완벽하게 준수하며 확장이 쉬움 |
| Map Registry | 전략 선택 기준이 **Key(이름)**로 명확할 때 | 성능이 가장 우수하며 코드가 직관적임 (실무 추천) |
| Enum | 로직이 단순하고 외부 의존성(DB 등)이 없을 때 | 파일 관리가 편하고 한눈에 들어옴 |

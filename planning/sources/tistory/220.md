# 퍼사드 패턴(Facade Pattern) 완벽 정리

원문: https://jinwookoh.tistory.com/220

"주문 버튼 하나를 눌렀을 뿐인데, 내부적으로는 재고 확인, 결제 요청, 포인트 차감, 이메일 발송, 배송 요청이 동시에 일어납니다."

클라이언트(프론트엔드 또는 컨트롤러)가 이 복잡한 로직을 모두 알게 하면 결합도가 너무 높아집니다. 이를 해결하기 위해 **건물의 정면(Facade)** 처럼 복잡한 내부를 가리고 **"통합된 인터페이스 하나만 제공"**하는 것이 퍼사드 패턴입니다.

하지만 이를 구현할 때, 자바 개발자는 **Static Method**의 유혹과 **Spring Bean**의 정석 사이에서 고민하게 됩니다.

## 1. 방식 1: 정적 퍼사드 (Static Helper) - "간편함"

흔히 ~Util, ~Helper라는 이름으로 만드는 방식입니다. 객체 생성 없이 어디서든 호출할 수 있어 편리하지만, 객체지향적인 관점에서는 안티 패턴에 가깝습니다.

### 특징

- static 메서드로만 구성되어 있습니다.

- 상태(Member Variable)를 가지지 않습니다.

### 코드 예시

Java

```
// 복잡한 라이브러리들 (Subsystems)
class ComplexMailLib { ... }
class ComplexFileLib { ... }

// 정적 퍼사드 (Helper)
public class EmailHelper {
    // 복잡한 설정을 미리 다 해놓고, 딱 필요한 메서드만 노출
    public static void sendSimpleMail(String to, String msg) {
        ComplexMailLib mail = new ComplexMailLib();
        mail.setSession(...);
        mail.setPort(465);
        mail.send(to, msg);
    }
}

// 사용 (Client)
// 어디서든 편하게 호출 가능
EmailHelper.sendSimpleMail("user@test.com", "Hello");

```

### 장단점

- 장점: 구현이 매우 쉽고, 인스턴스를 주입받을 필요가 없어 호출이 간편합니다.

- 단점: 테스트 불가능: EmailHelper.sendSimpleMail을 호출하는 코드를 테스트할 때, 실제 메일 발송을 막거나 Mocking 하기가 매우 어렵습니다. (PowerMock 같은 무거운 도구 필요)

- 확장 불가: 인터페이스 교체가 불가능하므로 유연성이 떨어집니다.

## 2. 방식 2: 서비스 퍼사드 (Interface-based Facade) - "스프링의 정석"

스프링과 같은 의존성 주입(DI) 컨테이너 환경에서 사용하는 표준 방식입니다. 퍼사드 자체가 **빈(Bean)**으로 등록되며, 다른 서비스들을 주입받아 **조율(Orchestration)**하는 역할을 합니다.

### 상황 (쇼핑몰 주문)

컨트롤러가 PaymentService, InventoryService, NotiService를 다 주입받아 호출하면 코드가 너무 지저분해집니다. 이를 OrderFacade로 묶습니다.

### 코드 예시

Java

```
@Service
@RequiredArgsConstructor
public class OrderFacade {
    // 하위 서브시스템들 (DI로 주입)
    private final InventoryService inventoryService;
    private final PaymentService paymentService;
    private final NotificationService notificationService;

    // "주문하다"라는 단순한 인터페이스 제공
    @Transactional // 트랜잭션을 여기서 묶을 수 있음 (큰 장점!)
    public void placeOrder(OrderDto orderDto) {
        // 1. 재고 확인 및 차감
        inventoryService.decreaseStock(orderDto.getProductId());

        // 2. 결제 진행
        paymentService.pay(orderDto.getCardInfo());

        // 3. 알림 발송 (실패해도 주문은 성공하게 try-catch 가능)
        try {
            notificationService.sendSms(orderDto.getUserPhone());
        } catch (Exception e) {
            // 로그만 남기고 무시
        }
    }
}

// 사용 (Controller)
@RestController
@RequiredArgsConstructor
public class OrderController {
    private final OrderFacade orderFacade; // 이것 하나만 알면 됨!

    @PostMapping("/order")
    public void order(@RequestBody OrderDto dto) {
        orderFacade.placeOrder(dto);
    }
}

```

### 장단점

- 장점: 테스트 용이: OrderFacade를 테스트할 때 하위 서비스들을 Mocking 하여 단위 테스트하기 쉽습니다.

- 트랜잭션 관리: 여러 서비스에 걸친 트랜잭션을 퍼사드 메서드 하나로 묶어 원자성(Atomicity)을 보장할 수 있습니다.

- 단점: 클래스 파일과 의존성 주입 설정이 늘어납니다.

## 3. 실무 예시: SLF4J (Simple Logging Facade for Java)

자바 개발자라면 누구나 쓰는 SLF4J가 이름 그대로 가장 대표적인 퍼사드 패턴입니다.

- Facade: org.slf4j.Logger (인터페이스)

- Subsystem: Log4j2, Logback, Java Util Logging (실제 구현체)

우리는 log.info()만 호출하면, 실제로는 뒤에 연결된 Logback이나 Log4j2가 복잡한 로직을 수행합니다. 덕분에 로깅 라이브러리를 바꿔도 애플리케이션 코드는 수정할 필요가 없습니다.

## 요약: 헬퍼를 쓸까, 퍼사드 빈을 만들까?

| 구분 | Static Helper (Utils) | Service Facade (Bean) |
|---|---|---|
| 호출 방식 | ClassName.method() | @Autowired 후 instance.method() |
| 목적 | 단순 유틸리티 기능 (날짜 변환 등) | 비즈니스 로직의 통합 및 조율 |
| 테스트 | 어려움 (Mocking 힘듦) | 쉬움 (Mock 객체 주입 가능) |
| 트랜잭션 | 적용 어려움 | @Transactional 적용 가능 |

### 결론

단순히 날짜 포맷을 맞추거나 문자열을 자르는 등의 **상태 없는(Stateless) 유틸리티 기능**이라면 **Static Helper** 방식이 좋습니다.

하지만 **여러 Service를 호출하여 흐름을 제어**해야 하거나, **트랜잭션**을 묶어야 한다면 반드시 **Service Facade(빈 등록)** 방식을 사용해야 합니다. 이것이 "객체지향적인" 설계이자 "테스트 가능한" 코드를 만드는 지름길입니다.

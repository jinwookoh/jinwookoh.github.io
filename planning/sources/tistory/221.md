# 중재자 패턴(Mediator Pattern) 완벽 정리

원문: https://jinwookoh.tistory.com/221

"비행기들이 서로 통신하며 착륙 순서를 정한다면 공항은 아수라장이 될 것입니다. 비행기는 오직 관제탑(Controller)하고만 교신해야 합니다."

소프트웨어도 마찬가지입니다. 회원 서비스가 주문 서비스를 부르고, 주문 서비스가 다시 포인트 서비스를 부르고, 포인트가 메일을 보낸다면... 의존성이 거미줄처럼 꼬이게 됩니다(Spaghetti Code).

이 복잡한 관계를 끊고 **"모든 대화는 나를 통하라"**고 정리해 주는 것이 **중재자 패턴**입니다. 하지만 이 중재자를 구현하는 방식은 크게 두 가지로 나뉩니다.

## 1. 방식 1: 클래식 중재자 (Direct Reference) - "채팅방 스타일"

GoF 디자인 패턴의 정석입니다. 중재자(Mediator)가 모든 참여자(Colleague)의 **참조(Reference)를 직접** 가지고 있고, 참여자들도 중재자를 알고 있는 **상호 의존적** 구조입니다.

### 특징

- 중앙집권: 모든 로직이 중재자 클래스 하나에 집중됩니다.

- 명시적 호출: 참여자가 "중재자님, 전달해 주세요"라고 직접 메서드를 호출합니다.

### 코드 예시 (채팅방)

Java

```java
// 1. 중재자 인터페이스
interface ChatMediator {
    void sendMessage(String msg, User user);
    void addUser(User user);
}

// 2. 참여자 (User)
abstract class User {
    protected ChatMediator mediator; // 중재자를 알고 있음
    protected String name;

    public User(ChatMediator med, String name) {
        this.mediator = med;
        this.name = name;
    }

    public abstract void send(String msg);
    public abstract void receive(String msg);
}

// 3. 구체적 중재자 (채팅방 구현)
class ChatRoomImpl implements ChatMediator {
    private List users = new ArrayList<>();

    @Override
    public void addUser(User user) { users.add(user); }

    @Override
    public void sendMessage(String msg, User sender) {
        // 나를 제외한 모두에게 메시지 전파 (중앙 통제)
        for (User u : users) {
            if (u != sender) {
                u.receive(msg);
            }
        }
    }
}

```

### 장단점

- 장점: 흐름을 한곳에서 파악하기 쉽습니다. (채팅방 클래스만 열어보면 로직이 다 보임)

- 단점: God Object: 로직이 복잡해지면 중재자 클래스가 수천 줄짜리 괴물이 됩니다.

- 강한 결합: 참여자(User)가 중재자(ChatMediator)를 필드로 가지고 있어야 해서 재사용이 어렵습니다.

## 2. 방식 2: 이벤트 기반 중재자 (Event-Driven) - "Spring 스타일"

현대적인 아키텍처에서는 참여자가 중재자를 모르게 만듭니다. 대신 **옵저버 패턴(Observer)**이나 **이벤트 버스**를 활용해 느슨하게 연결합니다.

### 특징

- 느슨한 결합: 참여자는 "사건(Event)"만 던지고, 누가 받는지 모릅니다.

- Spring ApplicationEvent: 스프링이 거대한 중재자 역할을 대신해 줍니다.

### 코드 예시 (주문 완료 후 로직 처리)

Java

```java
// 1. 이벤트 정의
class OrderCompletedEvent { /* 주문 정보 */ }

// 2. 참여자 (주문 서비스) - 중재자를 모름!
@Service
@RequiredArgsConstructor
public class OrderService {
    private final ApplicationEventPublisher publisher; // 스프링의 이벤트 버스

    public void placeOrder() {
        System.out.println("주문 완료");
        // "주문 끝났어!"라고 외치기만 함. 누가 듣는지는 관심 없음.
        publisher.publishEvent(new OrderCompletedEvent());
    }
}

// 3. 중재자 역할 (리스너들이 나눠서 처리)
@Component
class OrderEventHandler {

    @EventListener
    public void sendMail(OrderCompletedEvent event) {
        System.out.println("메일 발송");
    }

    @EventListener
    public void decreaseStock(OrderCompletedEvent event) {
        System.out.println("재고 차감");
    }
}

```

### 장단점

- 장점: 완벽한 분리: 주문 서비스는 메일 서비스나 재고 서비스를 전혀 참조하지 않습니다. (import 문도 없음)

- 확장성: 새로운 기능을 추가하고 싶으면 리스너만 하나 더 만들면 됩니다.

- 단점: 흐름이 분산되어 있어서, "주문 버튼을 눌렀을 때 무슨 일이 일어나는지" 한눈에 파악하기 어렵습니다. (IDE의 도움이 필요함)

## 3. 실무 예시: UI 프로그래밍 vs 백엔드

이 두 방식은 사용처가 명확히 갈립니다.

### 1) Java Swing / JavaFX / React Forms (Classic)

복잡한 입력 폼을 만들 때, "체크박스를 켜면 텍스트 필드가 활성화되고, 드롭다운을 바꾸면 버튼이 꺼지는" 로직이 필요합니다. 이때는 **클래식 중재자**를 사용하여 FormMediator 클래스 하나에 UI 제어 로직을 몰아넣는 것이 유지보수에 좋습니다.

### 2) Spring Backend / Microservices (Event-Driven)

서비스 간의 의존성을 끊어야 하는 백엔드에서는 **이벤트 기반 중재자**가 필수입니다. 결제 서비스가 배송 서비스를 직접 호출하는 순간, 두 서비스는 한 몸이 되어버리기 때문입니다.

## 요약: 독재자인가, 소통창구인가?

| 구분 | Classic Mediator (ChatRoom) | Event Mediator (Spring Event) |
|---|---|---|
| 연결 방식 | 직접 참조 (Hard Reference) | 이벤트/옵저버 (Pub/Sub) |
| 의존성 | 참여자가 중재자를 알고 있음 | 참여자는 중재자를 모름 |
| 로직 위치 | Mediator 클래스 내 if-else | 분산된 EventListener 메서드들 |
| 단점 | 중재자 클래스가 비대해짐 (God Class) | 전체 흐름 파악이 어려움 |
| 추천 상황 | 복잡한 UI 제어, 채팅방 로직 | 도메인 간 결합도 분리, 마이크로서비스 |

### 결론

서로 얽히고설킨 객체 관계를 풀어야 한다면 중재자 패턴이 정답입니다.

- 한 화면 안에서 컴포넌트끼리 지지고 볶아야 한다면 클래식 중재자를 만들어 로직을 중앙 통제하세요.

- 시스템 전체에서 모듈 간의 결합을 끊고 싶다면 **스프링 이벤트(Event Mediator)**를 사용하여 우아하게 소통하세요.

# API 버저닝 패턴(API Versioning Pattern) 완벽 정리

원문: https://jinwookoh.tistory.com/249

API는 한 번 배포되면 **계약(Contract)**이 됩니다. 함부로 수정하면 클라이언트가 오작동합니다. 그래서 우리는 v1, v2를 만듭니다.

하지만 이 버전 정보를 어디에 두느냐에 따라 API의 사용성(DX)과 캐싱 전략, 그리고 RESTful 원칙 준수 여부가 완전히 달라집니다.

## 1. 방식 1: URI 버저닝 (URI / Path Versioning) - "가장 실용적인 접근"

트위터, 페이스북, 구글 등 대다수의 **공용 API(Public API)**가 사용하는 방식입니다. URL 경로 자체에 버전 숫자를 박아버립니다.

### 특징

- 직관성: URL만 봐도 몇 번째 버전인지 알 수 있습니다.

- 리소스 분리: v1/users와 v2/users는 아예 다른 자원 취급을 받습니다.

### 코드 예시 (Spring Boot)

Java

```java
@RestController
public class MemberController {

    // 버전 1: 옛날 방식
    @GetMapping("/v1/members")
    public MemberV1 getMembersV1() {
        return new MemberV1("James");
    }

    // 버전 2: 이름 필드가 분리됨
    @GetMapping("/v2/members")
    public MemberV2 getMembersV2() {
        return new MemberV2("James", "Gosling");
    }
}

```

### 장단점

- 장점: 개발자 경험(DX): 브라우저 주소창에 쳐보기만 해도 테스트가 가능합니다. 매우 직관적입니다.

- 캐싱 용이: URL이 다르니 CDN이나 프록시 서버에서 별도 설정 없이도 캐싱이 완벽하게 분리됩니다.

- 단점: REST 원칙 위배: REST의 창시자(Roy Fielding)는 "리소스의 식별자(URI)에 버전을 넣지 말라"고 했습니다. User는 그냥 User이지 v1 User가 아니라는 철학입니다.

- URL 오염: 버전이 올라갈수록 URL 경로가 지저분해집니다.

## 2. 방식 2: 헤더 버저닝 (Header / Media Type Versioning) - "가장 RESTful한 접근"

깃허브(GitHub), 마이크로소프트 등 **REST 원칙을 엄격하게 지키는 곳**에서 사용하는 방식입니다. URL은 그대로 두고, HTTP 헤더에 버전 정보를 숨겨서 보냅니다.

### 특징

- 단일 URI: /users라는 URL은 변하지 않습니다.

- Content Negotiation: 클라이언트가 "나는 v2 형식의 JSON을 원해"라고 Accept 헤더나 커스텀 헤더로 요청합니다.

### 코드 예시 (Spring Boot)

Java

```
@RestController
@RequestMapping("/members")
public class MemberHeaderController {

    // 1. 커스텀 헤더 방식 (X-API-VERSION)
    @GetMapping(headers = "X-API-VERSION=1")
    public MemberV1 getMembersV1() { ... }

    // 2. 미디어 타입 방식 (Accept 헤더 - GitHub 스타일)
    // Accept: application/vnd.company.v2+json
    @GetMapping(produces = "application/vnd.company.v2+json")
    public MemberV2 getMembersV2() { ... }
}

```

### 장단점

- 장점: 깔끔한 URI: URL이 리소스 자체(members)만을 나타내므로 가장 RESTful 합니다.

- 유연성: 버전 변경이 URL 구조에 영향을 주지 않습니다.

- 단점: 테스트 불편: 브라우저 주소창만으로는 테스트할 수 없습니다. Postman이나 cURL을 써서 헤더를 조작해야 합니다.

- 캐싱 복잡: URL이 같기 때문에, CDN 캐시 설정 시 Vary 헤더를 통해 "헤더 값에 따라 다른 결과를 캐싱하라"고 별도로 알려줘야 합니다.

## 3. 실무 비교: 언제 무엇을 쓰는가?

| 구분 | URI Versioning (Path) | Header Versioning (Media Type) |
|---|---|---|
| 형태 | GET /v1/users | GET /users + Header: v1 |
| RESTful | 위배됨 (식별자 변경) | 준수함 (표현 방식 변경) |
| 사용성 (DX) | 매우 좋음 (직관적) | 다소 불편 (도구 필요) |
| 캐싱 난이도 | 쉬움 (URL 기준) | 어려움 (Vary 헤더 설정 필요) |
| 대표 사례 | Twitter, Google, Facebook, AWS | GitHub, Microsoft, Stripe |
| 추천 상황 | 일반적인 웹/앱 API, 빠른 개발이 중요할 때 | 엄격한 REST API, 사내 표준이 중요할 때 |

### 결론

"이론적으로 완벽한 것"과 "쓰기 편한 것"의 싸움입니다.

대부분의 실무, 특히 **스타트업이나 일반적인 기업 환경**에서는 **URI 버저닝(/v1/)**을 사용하는 것이 정신 건강에 좋습니다. 개발자도, 클라이언트도 가장 이해하기 쉽기 때문입니다.

하지만 **오픈 API 플랫폼**을 만들거나, **API의 수명이 매우 길고 변경이 잦은 엔터프라이즈 환경**이라면 **헤더 버저닝(Media Type)**을 도입하여 URL의 영속성을 지키는 것이 우아한 선택입니다.

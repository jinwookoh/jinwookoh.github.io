Claude Code란 무엇인가 — 설치와 기본 사용법

Claude Code는 저장소를 직접 읽고 고치고 명령을 실행하는 터미널 에이전트이며, 도입의 관문은 권한 모델이다

채팅 창에 코드를 붙여 넣고 답을 받아 다시 에디터로 옮기는 방식은 작업 범위가 파일 하나를 넘어가는 순간 무너진다. 모델은 저장소 전체를 보지 못하고, 테스트를 돌려 자기 답이 틀렸는지 확인할 방법도 없다. 관련 파일을 찾아 붙여 넣고, 결과를 옮겨 적고, 빌드 실패 로그를 다시 붙여 넣는 왕복이 전부 사람의 몫으로 남는다. Claude Code는 이 왕복을 도구 호출로 흡수한다. 파일을 직접 읽고 편집하며, 셸 명령을 실행해 그 출력을 다시 자기 입력으로 삼는다. 대신 관리 대상이 하나 늘어난다. 어떤 동작을 사람에게 묻지 않고 실행해도 되는지를 정하는 권한 모델이다.

핵심 개념

Claude Code는 에이전트 루프로 동작한다. 프롬프트를 받으면 도구를 호출하고, 그 결과를 관찰한 뒤 다음 도구를 호출하기를 목표가 끝날 때까지 반복한다. 내장 도구는 파일 읽기와 편집, 셸 실행, 패턴 검색, 웹 조회, 그리고 별도 컨텍스트에서 도는 서브에이전트 호출로 나뉜다. 사람이 파일을 첨부하지 않아도 필요한 파일을 스스로 찾아 읽는다는 점이 채팅형 도구와 갈리는 지점이다.

실행 표면은 여러 개다. 터미널 CLI가 가장 기능이 넓고, 그 밖에 VS Code와 JetBrains 확장, 데스크톱 앱, 브라우저에서 도는 웹 세션, Slack, GitHub Actions 같은 CI 통합이 있다. 표면은 달라도 엔진은 같아서 저장소의 CLAUDE.md, .claude/settings.json, MCP 서버 설정이 그대로 공유된다.

가장 먼저 이해해야 할 것은 권한 계층이다. 파일 읽기와 검색은 작업 디렉터리 안에서라면 묻지 않고 실행된다. 셸 명령, 파일 수정, 웹 조회는 승인 대상이다. 승인 방식은 권한 모드가 결정하며, 세션 중에 Shift+Tab으로 모드를 순환시킬 수 있다. Manual 모드의 설정값 이름은 default이고, 그 밖에 파일 편집만 자동 승인하는 acceptEdits, 탐색만 허용하는 plan, 별도 분류 모델이 사람 대신 검토하는 auto, 사전 승인된 도구만 허용하는 dontAsk, 검사를 건너뛰는 bypassPermissions가 있다.

Java 진영 개념으로 옮기면 대응이 뚜렷하다. 권한 규칙은 Spring Security의 요청 매처 체인처럼 첫 일치가 결과를 결정하며, 평가 순서는 deny 다음 ask 다음 allow로 고정돼 있고 규칙이 더 구체적이라고 순서가 바뀌지 않는다. CLAUDE.md는 매 세션 자동으로 읽히는 프로젝트 규약 파일로, 사용자 계층과 프로젝트 계층이 따로 있다는 점에서 application.yml과 프로필별 설정 파일의 관계에 대응한다.

인증은 Claude 구독 계정, Claude Console 계정, Bedrock·Vertex 같은 클라우드 제공자 중 하나로 한다. 환경에 ANTHROPIC_API_KEY가 설정돼 있으면 구독 로그인보다 그 키가 우선 적용되어 과금 경로가 조용히 바뀐다. 어떤 자격 증명이 활성인지는 /status로 확인한다.

코드

macOS·Linux·WSL 기준 설치와 첫 세션이다. 네이티브 설치본은 백그라운드에서 스스로 갱신된다.

curl -fsSL https://claude.ai/install.sh | bash

claude --version          # 버전 뒤에 (Claude Code) 가 출력되면 정상
cd /path/to/your/project
claude                    # 최초 실행 시 브라우저 로그인

비대화형 모드는 표준 입력을 받고 결과만 출력한 뒤 종료하므로 파이프라인에 그대로 끼워 넣는다. --output-format json은 result 필드를 가진 객체 하나를, stream-json은 한 줄에 객체 하나씩을 출력한다.

# 로그를 그대로 흘려 넣기
tail -200 app.log | claude -p "이 로그에서 이상 징후를 찾아 요약해"

# 변경된 파일만 리뷰
git diff main --name-only | claude -p "이 파일들의 보안 취약점을 점검해"

# 스크립트에서 파싱할 구조화 출력
claude -p "API 엔드포인트를 모두 나열해" --output-format json

프로젝트에 커밋해 팀 전체에 적용하는 최소 설정이다. 린트와 테스트는 묻지 않고 실행하되 비밀 파일 읽기는 막는다.

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}

실무에서 걸리는 지점

  • 세션이 시작하는 권한 모드가 환경마다 다르다. Pro·Max·Team 요금제의 대화형 터미널 세션은 auto로 시작하지만, claude -p 실행과 Agent SDK 세션은 요금제와 무관하게 Manual 모드로 시작한다. CI 스크립트에서 승인 프롬프트 때문에 멈추는 사고는 대부분 이 차이에서 나온다.
  • 되돌리기는 git을 대체하지 못한다. Esc를 두 번 누르거나 /rewind로 이전 체크포인트를 복원할 수 있지만, 체크포인트는 편집 도구를 거친 변경만 추적하므로 Bash 명령이나 외부 프로세스가 만든 변경은 복원되지 않는다.
  • 컨텍스트 윈도우가 성능을 좌우한다. 대화, 읽은 파일, 명령 출력이 모두 같은 윈도우에 쌓이고 채워질수록 앞선 지시를 놓치기 시작한다. 성격이 다른 작업 사이에는 /clear로 초기화하고, 탐색처럼 파일을 많이 읽는 일은 서브에이전트에 맡겨 본 대화 밖에서 처리한다.
  • 검증 수단이 없으면 완료 판단이 사람에게 남는다. 테스트, 빌드 종료 코드, 린터처럼 통과와 실패가 나오는 검사를 함께 주지 않으면 에이전트는 "그럴듯해 보임"을 완료 신호로 쓴다.
  • 패키지 관리자별로 갱신 방식이 다르다. Homebrew와 WinGet으로 설치한 경우 자동 갱신되지 않으므로 brew upgrade나 winget upgrade를 주기적으로 직접 실행해야 한다.
